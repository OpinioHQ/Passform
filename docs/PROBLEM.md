# 문제 정의서 — Passform

> 이 문서는 **왜** 만드는가에 답한다. 무엇을 만드는가는 `docs/SPEC.md`, 도메인 구조는 `docs/ontology.yaml`이 정본이다.
> 로그 번호와 관찰 번호는 `docs/research/interviews.md`(강의 2)의 번호다. 따옴표 안은 기록 원문이고, 따옴표 없는 문장은 요약이다.

## 1. 한 문장 문제

학교·직장 등 소속·단체 활동에서 여러 폼에 반복 응답하는 사람은 마감·작성 중 분량·제출한 답을 확인하고 관리하는 데 어려움을 겪으며, 기한을 놓쳐 제출에 실패하거나 긴 폼의 작성을 중단하고 제출 후에도 제대로 냈는지 불안해한다.

> 2차 문제(제작자): 폼을 만들어 응답을 모으는 제작자는 모인 응답의 확인·정리·가공에 부담을 겪고, 응답 화면과 엑셀 시트를 오가거나 수작업을 동원하기도 한다(로그 1·2·8, 관찰 1).

## 2. 대상과 비대상

- 1차 사용자(응답자): 학교·직장·동아리·단체 등 소속 활동에서 신청·설문 폼에 반복해서 응답하는 사람.
- 2차 사용자(제작자): 그런 폼을 만들어 응답을 모으고 선발·명단 정리에 쓰는 사람.
- 초기 우선 대상: SPEC 2절의 대학생 응답자와 대학생 운영진. 동아리 가입, 학생회 행사, 학과 신청 등의 상황부터 검증한다. 이는 초기 집중 대상이며, 이용자·테스터를 대학생으로만 제한하는 조건은 아니다.
- 비대상 사용자: 소속과 무관하게 일회성으로 응답하는 사람(예: 마케팅·고객 만족도 설문 응답자).
- MVP에서 우선 해결하지 않는 과업(비대상): 직장 만족도 설문의 문항 내용·선택지 품질 개선, 보상형 설문의 보상 불신 해결, 연구·학술 설문의 평균·교차분석·검정, 회비의 실제 송금·입금 대조. 실제 구현의 포함·비포함은 SPEC 4절을 따른다.

SPEC의 타깃·비대상은 현재 기능 선정의 우선순위와 해결 과업의 경계로 두며, 테스트 참여나 인터뷰 근거의 사용을 금지하는 조건으로 적용하지 않는다. 인터뷰 근거는 직업보다 해당 문제를 실제로 경험했는지를 기준으로 채택한다. 전체 표본의 집계와 대학생 등 하위 집단의 집계는 분모·분자를 명시해 구분한다.

## 3. 증거

응답자

- 응답 전: 받은 폼의 마감을 놓친다. "마감일이 지나서 폼 제출을 못한 적이 많아요" (로그 2, 대학생) / 나중에 응답하려다 마감을 놓친 경험(로그 7, 직장인). 두 로그 모두 마감 누락 문제의 근거로 사용한다.
- 작성 중: 폼의 전체 분량을 가늠하기 어렵다. “페이지가 계속 넘어가는데 전체 챕터가 얼마나 남았는지 안 떠서 소요 시간을 알 수 없는 게 제일 불편해요.” (로그 9) / 같은 페인: 로그 4 (`전체분량_파악_어려움`). 현재 진행률 파악은 로그 9에 기록된 별도 신호다.
- 작성 중단: 긴 설문에서 중도 이탈한 경험이 로그 4에 기록됐고, 로그 8에는 설문 도중 다른 일을 해야 해서 중단한 경험이 많다는 진술이(설문 길이를 직접 언급하지는 않음), 로그 9에는 `장문설문_중단` 태그와 관련 페인이 기록됐다. 로그 4·8·9를 모두 해당 페인의 근거로 사용한다. 전체 분량 파악의 어려움과 중단이 함께 확인되지만, 그 어려움이 모든 중단의 원인이라고 확정하지 않는다.
- 작성 중: 앞에서 쓴 답을 다시 확인하기 어렵다. 로그 2는 작성 중 앞 문항에 쓴 답을 잊어 다시 확인하기 불편했다고, 로그 6은 작성 중 앞선 응답을 확인하기 어렵다고 진술했다(응답자 페인 10). 제출한 뒤 답을 다시 보는 문제와 구분한다. 분기가 없는 폼에서는 응답자가 「전체 질문 보기」로 바꿔 앞선 답을 한 페이지에서 볼 수 있지만(SPEC 4절 응답 화면 보기 방식, AC47), 이 문제를 직접 겨냥한 기능은 아니며 분기가 있는 폼에서는 보기 전환을 제공하지 않는다.
- 제출 후: 무엇을 썼는지 확인할 수 없어 불안하다. "제출 누르면 '내가 제대로 썼나?' 싶어서 불안해요. 완료 후에 내가 선택한 전체 내용을 확인할 수 있으면 좋겠어요." (로그 6) / 같은 페인: 로그 3, 4, 10 (응답자 페인 1). 로그 10은 이전에 작성한 폼 등 과거 이력을 확인하려고 외부 창을 오갔다고 진술했다(과거 이력을 이전에 작성한 폼으로 해석).
- 제출 후: 제출한 답을 스스로 수정하기 어렵다. 로그 3은 응답 내용을 확인하는 것과 함께 수정하는 것도 어렵다고 진술했다(1건, 1개 이하 응답자 페인 8). MVP의 응답 수정 허용(SPEC AC16, AC74)은 이 문제에 대응한다.
- 제출 후 관련 설정의 사용 맥락: 기존 폼 서비스에서 제작자가 응답 사본 전송·수정 허용 등이 포함된 상세 설정을 다뤘다(로그 3의 대상, 관찰 1 ⑥). 해당 항목을 실제로 켰는지와 선택 이유는 기록되어 있지 않으므로 응답자의 확인 요구를 직접 관찰한 근거로 세지 않는다. 이 기록은 기존 대안의 사용 맥락이며, MVP에 응답 사본 전송 기능을 추가한다는 뜻은 아니다.
- 같은 기본 정보를 폼마다 다시 쓴다. "이름이나 전화번호처럼 매번 똑같이 쓰는 기본 정보는 알아서 자동으로 입력되면 좋겠어요." (로그 3) / 같은 페인: 로그 8 — 주민등록번호를 자주 직접 입력했고, 직접 치면 실수할 수 있다고 우려했다(응답자 페인 9). 주민등록번호는 프로필 저장 대상이 아니므로(SPEC 4절 비포함), 로그 8은 반복 입력 문제의 근거일 뿐 그 값을 자동채우기로 해결한다는 뜻은 아니다.
- 개인정보를 내는 것 자체가 불안하다. "설문조사에 개인정보를 제출해야하는 것이 불안해요" (로그 4) / 같은 태그: 로그 9 — 정보를 저장해 주는 방식이 이 불안을 키울 수 있다(Job Story 2의 Anxiety). 그래서 프로필 저장 항목을 닫힌 목록으로 제한하고, 프로필 삭제를 허용하며, 수집 범위를 동의 문구로 보여 준다(SPEC AC3, AC5, AC13).
- 작성 중 답의 글자 수를 확인하고 문장을 다듬으려고 폼 밖으로 이동한다. 로그 10의 대상인 대학생을 재현 관찰한 관찰 2에서는 글자 수 세기 서비스와 AI 윤문 도구를 오가며 외부 창으로 6번 이동했다. 두 목적이 합쳐진 횟수이며, 글자 수 확인만의 횟수는 분리되어 있지 않다. MVP의 글자 수 표시·최대 글자 수 설정은 이 중 글자 수 확인 수고를 줄이려는 기능이다.
- 송금하려고도 폼 밖으로 나간다. "계좌이체나 과거 이력 등을 확인하려고 외부 창을 자주 왔다 갔다 하는데, 이 때문에 설문 흐름이 끊기는 경우가 많아요." (로그 10) / 관찰 2에서 계좌번호를 보고 은행 앱으로 1번 이동했다. 송금 링크는 계좌번호를 옮겨 적는 수고만 줄인다 — 로그 3의 "'송금완료' 체크만 해두고 실제론 돈을 안 내는" 입금 대조 문제는 링크로 풀리지 않고 범위 밖이다.
- **반대 신호:** 관찰 2에서 각종 개인정보 입력은 30초 안에 끝났다. 시간이 오래 걸린 것은 주관식 2문항(각 5~10분)이었다. 이 사례만으로 자동채우기의 작성 시간 단축 효과를 주장할 수 없으므로 작성 시간 단축을 성공 지표로 쓰지 않는다. 자동채우기에 기대하는 효과는 시간 단축이 아니라 같은 정보를 반복 입력하는 수고와 오입력을 줄이는 것으로 한정한다(로그 3, 8). 주관식 내용 자체를 AI로 다듬는 기능은 캡디 추가 개발 2순위로 둔다.

응답 전·작성 중·제출 후의 불편은 각각 다른 로그에서 확인했다. 작성 중의 외부 도구 이동은 화면 공유로도 관찰했지만, 세 단계 모두가 한 사람에게서 직접 관찰됐다고 주장하지 않는다. 로그 7의 마감 누락과 로그 8의 기본정보 반복 입력·설문 중단은 각각 해당 페인의 근거다. 직업을 이유로 제외하지 않으며, 각 로그에 기록되지 않은 문제까지 경험했다고 확장하지 않는다.

제작자

- 응답을 확인하려고 응답 탭(통계)과 연동 시트를 5번 번갈아 보고, 면접 단계에서는 창을 나눠 폼과 시트를 함께 띄웠다. 본인은 기존 템플릿과 회의록을 보느라 이동이 많았다고만 진술했다 — 응답 확인 단계의 전환은 관찰에서 처음 드러났다. ⑧에서는 시트에서 응답을 여러 기준으로 정렬했고, 시트에 필터가 적용된 것도 확인했다. (관찰 1 ⑦·⑧, 로그 3의 인터뷰 대상자)
- "결과를 엑셀과 연동해서 사용하는 것이 어려웠어요" (로그 2) / "나는 그냥 엑셀로 바로 가가지고 엑셀 상에서 조작을 해가지고" (로그 8) / 로그 1에는 분석 기능 부족이 페인으로 기록됐다(제작자 페인 1).
- 질문 수가 많으면 문항을 하나씩 만들어야 한다. "질문의 수가 많을 때 따로따로 다 만드는게 힘들었어요" (로그 1). 로그 3의 기본문항 자동 생성 요구는 해결책에 대한 요구이며, 반복 제작 경험의 두 번째 사례로 세지 않는다. 과거 양식을 참고하는 행동은 관찰 1에서 다른 설문지를 4번 연 것으로 확인했다.

## 4. 반증 조건

### 문제의 실재 (인터뷰 증거로 지금 판정)

기준선은 단골 예시와 같은 비율(대상의 30%)이다. 이 기준은 로그를 본 뒤에 정했으므로, 다음 인터뷰 라운드(사용자 테스트 사전 인터뷰 포함)에서 같은 기준으로 다시 판정한다.

**층 A — 응답자**

- 주장: 소속 활동에서 폼을 사용하는 응답자는 마감 누락, 작성 중 전체 분량 파악의 어려움, 장문 설문 중단, 제출 내용 재확인의 어려움 중 하나 이상을 겪는다. 초기 검증에서는 대학생을 우선 모집하되 다른 응답자도 포함한다.
- 반증 조건: 폼 응답 경험이 있는 인터뷰 대상 중 위 문제를 하나 이상 겪은 사실이 인용·태그·로그별 페인에 기록된 사람이 **30% 미만이면 기각**한다. 직업에 관계없이 같은 기준으로 판정한다.
- 현재 집계: 인터뷰 10명(로그 1~10) 중 8명(로그 2, 3, 4, 6, 7, 8, 9, 10) = 80% → **유지.** 로그 7은 마감 누락, 로그 8은 설문 중단, 로그 10은 제출 내용 재확인(과거 이력을 이전에 작성한 폼으로 해석)으로 포함한다. 로그 10을 빼도 7명 = 70%로 유지된다. 로그 3·4의 제출 내용 재확인 어려움과 로그 8·9의 중단은 태그·페인 설명으로, 로그 9의 전체 분량 파악 어려움은 인용과 태그로 확인했다. 로그 5의 실시간 현황 요구는 별도 페인으로 사용하되 위 집계에 포함하지 않는다.
- 대학생 하위 집단: 8명(로그 1, 2, 3, 4, 6, 8, 9, 10 — 로그 8은 직장인이자 대학생) 중 7명(로그 2, 3, 4, 6, 8, 9, 10) = 약 88%. 이는 대학생 표본의 비율이며, 전체 표본 80%와 구분해 표기한다. 관찰 사례는 별도 인터뷰 인원으로 더하지 않는다.

**층 B — 제작자**

- 주장: 응답을 모으는 제작자는 모인 응답의 확인·분석·연동·가공에 부담을 겪고, 폼 밖 도구나 수작업을 동원하기도 한다.
- 반증 조건: 폼 제작 경험이 있는 인터뷰 대상 중 응답의 확인·분석·연동·가공 부담이 기록된 사람이 **30% 미만이면 기각**한다. 직업에 관계없이 같은 기준으로 판정한다.
- 현재 집계: 제작 경험자 5명(로그 1, 2, 3, 6, 8) 중 4명(로그 1, 2, 3, 8) = 80% → **유지, 약한 근거.** 행동으로 확인한 것은 관찰 1(로그 3의 인터뷰 대상자) 1명이고, 로그 2와 로그 8은 진술(로그 8은 엑셀로 바로 옮겨 직접 조작한다고 진술), 로그 1의 분석 기능 부족은 팀의 페인 코딩이다. 4명이 모두 외부 도구를 사용한 행동이 관찰됐다는 뜻은 아니다. 제작 경험자 5명이 모두 대학생(로그 8은 직장인이자 대학생)이어서 대학생 하위 집단의 비율도 80%로 같다. 다음 인터뷰에서 "지난번 폼 응답을 마지막으로 정리한 게 언제였고, 어떻게 했나요?"로 행동을 확인한다.
- 로그 6 제외 이유: `응답형식_불일치`는 전화번호 등 입력 필드의 형식이 통일되지 않은 문제의 근거다. 해당 로그에는 외부 도구나 수작업으로 결과를 확인·정리한 행동 또는 결과 연동의 부담이 명시되어 있지 않아 층 B의 사례로 세지 않는다.

### 해결 가설 (제품 사용 관찰로 이후 판정 — MVP 사용자 테스트)

- 가설 1a(제출 이력): 로그인 응답자가 제출한 문항·답을 다시 확인할 수 있으면, 무엇을 제출했는지 알아보려고 제작자에게 문의하거나 별도 기록을 찾는 수고가 줄어든다.
  - 반증 조건: 사용성 세션에서 과거 문항·답을 확인하는 과제를 줬을 때, **본인 제출 이력이 정상 조회되는데도** 도움 없이 답을 찾지 못해 제작자에게 문의하거나 별도 기록을 찾아 재확인하면 기각한다. 이력의 조회 실패·누락은 이력 품질(SPEC AC15)의 문제로 따로 센다. 동일 폼에 다시 제출했다는 사실만으로는 기각하지 않는다.
- 가설 1b(자동채우기): 저장한 프로필로 응답자 본인 정보 문항을 채울 수 있으면, 같은 기본 정보를 폼마다 직접 입력하는 수고가 줄어든다.
  - 반증 조건: 본인 정보 문항과 해당 값이 저장된 프로필을 사용하는 세션 과제에서, **값이 맞게 제안됐는데도** 지우고 같은 값을 다시 입력하거나 자동채우기 가능한 다음 폼에서도 직접 입력하면 기각한다. 값이 잘못 제안돼 고친 경우는 자동채우기 품질(SPEC AC6)의 문제로 따로 센다. 다른 값으로 바꾸려는 의도적인 수정은 반복 입력 실패로 세지 않는다.
- 가설 2(내 폼함·마감 알림): 받은 폼을 내 폼함에 저장하고 마감 전에 알려 주면, 응답자의 마감 전 제출률이 높아진다.
  - 반증 조건: 사용자 테스트에서 참가자를 알림 켬·끔 그룹으로 나눴을 때(`PATCH /me/settings`), **알림이 정상 발송됐는데도** 켠 그룹의 마감 전 제출률이 끈 그룹보다 높지 않으면 기각한다. 발송 실패·중복 발송은 알림 품질(SPEC AC18)의 문제로 따로 센다.
- 가설 3(AI 결과 탐색): 자연어 한 줄 요청을 실제 문항·선택지에 매칭해 세거나 나열하고 어떻게 매칭했는지 함께 보여 주면, 제작자는 응답을 시트로 옮겨 다시 세지 않는다.
  - 반증 조건: 사용성 세션에서 관찰 1 ⑦·⑧단계(응답 확인, 시트 정렬·필터)와 같은 과제를 줬을 때, **요청대로 매칭된 결과를 받고도** 시트를 열어 같은 조건으로 다시 세면 기각한다. 매칭이 틀려서 다시 센 경우는 매칭 품질(SPEC AC21)의 문제로 따로 센다.
- 가설 4a(진행 표시): 현재 위치와 확정 가능한 남은 분량을 보여 주면, 응답자는 다른 페이지를 되짚거나 문항을 직접 세지 않고 남은 작업을 파악할 수 있다.
  - 반증 조건: 사용성 세션에서 **현재 위치와 확정 가능한 남은 분량이 정상 표시됐는데도** 도움 없이 그 정보를 파악하지 못하거나, 확인하려고 다른 페이지를 되짚고 문항을 직접 세면 기각한다. 표시·계산 오류는 진행 표시 품질(SPEC AC60)의 문제로 따로 센다. 분기가 미정인 경우 전체 문항 수나 백분율을 알아내는 것을 성공 조건으로 요구하지 않는다.
- 가설 4b(자동 임시 저장): 작성 중인 답을 저장해 다시 열 때 복원하면, 응답자는 잠시 중단해도 이전 답을 다시 입력하는 수고 없이 이어서 작성할 수 있다.
  - 반증 조건: 잠시 중단한 뒤 이어 쓰는 세션 과제에서 **저장된 답이 지원 조건에 맞게 정상 복원됐는데도** 초안을 찾아 이어 쓰지 못해 처음부터 다시 작성하거나 별도 기록을 찾아 이전 답을 재입력하면 기각한다. 저장·복원 오류는 임시 저장 품질(SPEC AC82·AC83)의 문제로 따로 센다. 잠시 화면을 나갔다가 이어 쓰는 행동 자체는 실패로 세지 않는다.
  - 과제 조건: 동일한 폼 버전이 열려 있고 마감 전인 경우에 평가한다. 첨부 파일을 포함한 복원 과제는 같은 기기·브라우저에서 진행한다. 브라우저 저장 내용 삭제나 의도적인 답변 변경은 이전 답의 손실로 세지 않는다.

## 5. 성공의 정의

MVP 배포 후 100명 이상을 대상으로 한 사용자 테스트에서 잰다. 대학생 응답자·운영진을 우선 모집하되 대학생이 아닌 참여자도 모집한다. 대학생 모집에 한계가 있어도 테스트 인원을 대학생으로만 제한하지 않는다. 전체 참여자의 결과를 집계하고, 역할·소속·폼 사용 경험별 차이도 함께 확인한다. 과업 성공은 사용성 세션의 관찰 기록으로, 제출·복귀는 테스트 기간의 관찰 기록과 후속 확인으로 측정한다. 비교할 폼·과제·그룹과 측정 기간은 테스트 시작 전에 정한다. 이 평가는 사용자 테스트의 측정 계획이며, 제품으로 제공하는 분석 범위는 SPEC 4절을 따른다.

응답자

- 마감 전 제출률: 내 폼함에 저장한 폼 중 마감 전에 제출한 비율(알림 켠 그룹 / 끈 그룹)
- 제출 이력 확인 성공률: 로그인 응답자가 도움 없이 자신의 과거 문항·답변을 제출 이력에서 찾아 확인한 비율
- 자동채우기 사용률: 해당 본인 정보 문항과 값이 저장된 프로필을 가진 로그인 응답자 중 프로필로 채운 비율
- 채운 값 유지율: 자동으로 채운 값을 고치지 않고 제출한 비율
- 프로필 저장 거부·삭제율: 개인정보 불안의 신호. 높으면 저장 방식이 신뢰를 얻지 못한 것이다
- 진행 정보 파악 성공률(가설 4a): 해당 정보를 정상 표시한 과제에서 현재 위치와 확정 가능한 남은 분량을 도움 없이, 다른 페이지를 되짚거나 문항을 직접 세지 않고 파악한 비율. 분기가 미정인 경우 확정되지 않은 전체 분량은 평가하지 않는다.
- 임시 저장 후 이어 쓰기 성공률(가설 4b): 지원 조건에 맞게 답이 복원된 과제에서 저장된 초안을 찾아 이전 답을 재입력하지 않고 이어서 작성한 비율. 의도적인 답변 수정은 재입력 실패로 세지 않는다.
- 보조 지표 — 작성 시작 대비 제출 완료율: 정한 테스트 기간에 작성을 시작한 사례 중 그 기간 안에 제출을 완료한 비율. 중단했다가 이어 써서 제출한 사례도 완료로 센다.
- 보조 지표 — 임시 저장 후 이어 쓰기 복귀율: 저장 완료 후 중단한 사례 중 정한 관찰 기간 안에 다시 열어 이어 쓴 비율. 미복귀만으로 진행 표시·임시 저장 가설을 기각하지 않고, 중단·미복귀 이유를 후속 확인한다.

제작자

- 분석 완결률: AI 결과 탐색 요청 중 결과(`status: ok`)까지 간 비율 — 되묻기 후 다시 말하거나 확정 요청을 보내 결과에 도달한 경우를 포함한다
- 사용성 세션 지표: 관찰 1 ⑦단계 과제 재현 시 폼 밖 전환 횟수(기준값 5번)

공통

- 핵심 시나리오 과업 성공률 95% 이상: 주요 사용자 시나리오(프로필 등록 → 자동채우기 → 제출 → 이력 확인, 폼 생성 → QR 배포 → 결과 탐색 등)를 사용자가 도움 없이 끝낸 비율. 계획서의 "주요 사용자 시나리오 기반 핵심 기능 테스트 95% 이상 통과"를 사용자 테스트의 과업 성공률로 정했다
- 보조 지표: Likert 평균 만족도 4.0 이상(계획서 목표). 의견 지표라 위의 행동 지표와 함께 해석한다
