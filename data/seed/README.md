# data/seed — 골든 테스트 fixture 초안

AI 결과 탐색의 평가 함수(조건 판정)를 검사할 입력 데이터다. **초안이며 사람이 검토·수정한 뒤 확정한다.**
기대 결과(몇 건이 일치하는지 등)는 여기에 적지 않는다. 기대 결과는 사람이 `tests/harness/golden_cases.yaml`에 쓴다.
현재 데이터는 모든 골든 케이스를 커버하지 않는다. 
밑의 파일별 목적에서 어떤 케이스를 커버하는 데이터인지 기술한다.
데이터 표에서는 각 데이터가 어느 수용기준과 케이스를 커버하는지 자세히 기술한다.

모든 데이터는 가상이다.

## 파일별 목적

| 파일 | 목적 |
|---|---|
| `forms/form_a_versions.json` | AC78의 구성(버전 1 소프트웨어학과 2건, 버전 2 소프트웨어학과 3건, 학과 문항이 없는 버전 3 4건)을 그대로 재현한다. **다른 응답을 추가하지 않는다.** |
| `forms/form_b_mixed.json` | 정상 응답과 함정 응답, 정상 문항과 함정 문항을 섞어 all/any/not, 미응답, 판정 불가, 모호한 조건, 데이터 취급을 검사한다. |
| `forms/form_summary.json` | AI 요약을 켠 폼이다. 입력 형식·본인 정보 설정이 다른 문항과 장문 문항을 섞고, AI 요약 동의·미동의 응답과 장문 속 연락처를 담아 요약 전송 범위를 검사한다. |
| `forms/form_required_branch.json` | 분기로 건너뛰는 섹션에 필수 문항이 있는 폼이다. 버전 2개로 제출 검증과 옛 버전 제출을 검사한다. |

파일 형식은 SPEC 5절 내보내기 JSON에 `form_id`와 응답별 `status`를 더한 것이다.

## 가정한 것

SPEC에 정해지지 않은 표현을 임시로 정한 것이다. 사람이 확정한다.

1. **값의 형태**: 단일 선택과 주관식의 `value`는 문자열, checkbox의 `value`는 하나만 골라도 문자열 배열이다. 선택지 값은 정의의 문구 그대로 쓴다.
2. **미응답의 표현 (확정)**: 비운 문항은 분기로 건너뛴 문항과 똑같이 `answers`에서 뺀다. `null`이나 `[]`를 쓰지 않는다. 건너뛴 문항을 빼는 것은 AC9에 따른 것이고, 비운 문항을 빼는 것은 사람이 확정했다. 그래서 둘의 구분은 `q5` 답으로 경로를 다시 계산해야 가능하다.
3. **미제출 응답의 시각**: `in_progress`는 SPEC대로 `submitted_at`과 `updated_at`이 `null`이다. `abandoned`도 같게 두었다. `abandoned` 판정 기준은 추가 개발 5로 미뤄져 있다.
4. **`updated_at`**: 두 폼 모두 `settings.editable: false`이므로 모든 응답에서 `null`이다.
5. **선택형이 아닌 문항의 `options`**: `[]`로 둔다.
6. **폼 정의 필드**: `form.schema.json`이 아직 없어 SPEC 5절 예시의 필드에 `settings.response_limit: null`을 더했다. 선택 필드(`input_format`, `question_description`, `character_limit`)는 넣지 않았다.
7. **`consent_template_id`**: 고정값 `consent_default`를 쓴다. 이 템플릿은 fixture에 없으므로 로더가 준비해야 한다.
8. **버전 수**: `form_b`는 버전 3개다. 소속 학과와 희망 학과를 다른 버전에 두면서 `q1`이 있는 버전의 변경도 함께 담기 위해서다.
9. **모호한 조건의 범위**: 소속 학과와 희망 학과의 선택지는 "경영학과"만 겹친다. "소프트웨어학과"까지 겹치면 그 조건이 항상 되묻기가 되어 all/any/not 판정을 검사할 수 없다.
10. **제출 시각**: 새 제출은 최신 버전으로만 가능하므로(`form_version_changed`) 앞 버전의 제출 시각이 항상 뒤 버전보다 빠르다. ID 순서와 시각 순서는 버전 안과 전체에서 모두 다르다.
11. **배열 순서**: `responses` 배열은 `response_id` 오름차순이다. 내보내기 순서가 아니므로 정렬 검사는 출력 쪽에서 해야 한다.
12. **문항 비필수**: 비운 응답을 만들기 위해 `q3`, `q4`, `q6`은 `required: false`다. `q6`을 필수로 두면 경로상 비운 응답이 유효하지 않게 된다.
13. **추가한 함정**: `rb14`(주관식 원문의 학과명)와 `form_b` v2의 `q1` 선택지 문구 변경은 요청 목록에 없던 것을 더했다. 필요 없으면 지운다.
14. **비운 문항의 선택지 조건 (확정)**: 경로상 만났지만 비운 문항의 선택지 조건은 판정 불가가 아니라 거짓이다. 사람이 확정했다. 분기로 건너뛴 문항은 판정 불가로 남는다(SPEC 5절).
15. **바뀐 선택지 문구 (확정)**: `form_b`의 "컴퓨터공학과"(v1)와 "컴퓨터공학부"(v2)는 다른 선택지다. 사람이 확정했다. 그래서 "컴퓨터공학과" 조건에서 v2 응답은 그 선택지가 없는 버전의 응답으로 판정한다(SPEC 5절).
16. **`ai_summary_agreed` (확정)**: 새 fixture(`form_summary`, `form_required_branch`)는 모든 응답에 `true`/`false`를 적는다. 키가 없는 기존 fixture(`form_a`, `form_b`)는 `false`로 읽는다. 사람이 확정했다. 작성 중 응답은 제출 때만 동의를 받으므로(SPEC 5절 212행) `false`다.
17. **AI summary 고지 (확정)**: 첫 배포 때 기록하는 `consent.ai_summary` 고지는 폼 정의 스키마 밖이라 fixture에 넣지 않고 `consent_default`처럼 로더가 준비한다. 사람이 확정했다.
18. **`form_required_branch`의 버전 (확정)**: 제출 케이스를 한 fixture로 쓰도록 버전 2개를 둔다. 옛 버전 제출을 만들기 위한 것이라 v2는 `q1` 문구만 다르다. 사람이 확정했다.
19. **`form_required_branch`의 ai_summary**: `settings.ai_summary`를 두지 않는다. 없으면 꺼짐이다(ARCHITECTURE 10절 F2). 그래서 이 폼의 `ai_summary_agreed`는 모두 `false`다.
20. **입력 형식 문항의 값**: `q2`처럼 형식이 있는 문항의 값은 저장 규칙을 적용한 뒤의 값으로 적는다(휴대전화는 숫자만). 장문 속 연락처는 원문 그대로 둔다.
