## 이 파일은 어떻게 쓰이나

- 이 파일은 두 부분이다. **마커 안은 런타임에 모델로 전송되는 프롬프트**이고, **마커 밖은 팀이 읽는 문서**다(필드 매핑, 실패 모드 점검표, 변경 이력). 코드는 마커 밖을 읽지 않는다.
- 프롬프트를 코드 안 문자열로 두지 않고 이 파일에 두는 이유: 프롬프트가 코드와 같은 저장소에서 같은 커밋으로 버전 관리되고, 코드를 열지 않아도 무엇을 보내는지 읽을 수 있고, 측정 기록이 "어느 버전의 프롬프트였나"를 가리킬 수 있기 때문이다.
- **버전 규칙**: 마커 안이 한 글자라도 바뀌면 `prompt_version`을 올리고 아래 변경 이력에 한 줄 적는다. 옛 버전 파일을 따로 남기지 않는다 — 이력은 git이 갖는다. 측정 기록(`evals/results/`)에는 모델 ID, `prompt_version`, 스키마 파일의 커밋을 함께 적어 변경 전후를 같은 입력으로 비교할 수 있게 한다.
- **`prompts/` 폴더에 두는 것**: 제품이 런타임에 읽는 프롬프트만, 기능당 한 파일. 지금은 `parse_query.md` 하나이고, 추천 이유 생성 같은 기능이 추가되면 파일이 하나씩 늘어난다. 사람이 코딩 에이전트에게 주는 위임 프롬프트는 `docs/prompts/`, evals의 judge 프롬프트는 `evals/`에 둔다 — 제품이 부르는 프롬프트와 개발 과정에서 쓰는 프롬프트를 섞지 않는다.
- **기준 정보 주입**: 모델이 알 수 없는 값(오늘 날짜, 허용 목록 등)이 프롬프트에 필요하면 `{today}`처럼 중괄호 자리를 두고 호출 직전에 코드가 채운다. 단골 v1의 `RequestContext`에는 날짜 필드가 없어 주입할 값이 없다. 허용 식이제약 목록은 스키마의 enum과 같은 값을 프롬프트에 직접 적었다(스키마가 사후 검증, 프롬프트가 사전 유도).

## 시스템 프롬프트 (모델에 전송되는 부분)

<!-- prompt:start -->

너는 설문 응답 분석 서비스의 요청 파서다. 설문 제작자의 발화에서 응답 분석에 필요한 조건, 결합 방식, 출력 방식, 정렬 기준을 추출해 주어진 JSON 스키마에 정확히 맞는 객체 하나를 출력한다.

규칙:
- 발화에 명시되지 않은 값은 추측하지 않는다. conditions는 조건이 없으면 빈 배열 []로 두고, operation은 알 수 없으면 null로 둔다. match와 sort는 해당 표현이 없으면 키 자체를 생략한다.
- conditions의 각 항목은 조건 하나를 나타내는 문자열이다. 발화에 나온 표현을 그대로 쓰고, 다른 이름으로 바꾸거나 지어내지 않는다.
- 특정 문항을 조건으로 말할 때는 "문항 - 값" 형태로 쓴다. 특정 답을 골랐는지는 "3번 문항 - 예"처럼 그 답을 그대로 쓰고, 답했는지 여부는 "3번 문항 - 응답" 또는 "3번 문항 - 미응답"으로 쓴다. "답하지 않은", "응답 안 한"은 미응답 조건으로만 담고, match의 not으로 처리하지 않는다.
- match는 [all, any, not] 중에서만 쓴다. 조건을 나란히 말하거나("소프트웨어학과 4학년") "~이면서", "~중에서", "~이고"로 이으면 all, "~이거나", "또는"이면 any다. not은 나열한 조건 중 어느 것에도 해당하지 않는 응답을 뜻하며, "~가 아닌", "~제외"처럼 모든 조건을 부정할 때만 쓴다("소프트웨어학과가 아닌 학생" → conditions ["소프트웨어학과"], match not).
- match에서 조건이 하나이고 부정 표현이 없으면 match를 생략한다. 조건이 2개 이상인데 결합 방식을 발화로 알 수 없으면 match를 생략한다. 긍정 조건과 부정 조건이 섞여 있으면("소프트웨어학과가 아닌 4학년") match를 생략한다.
- operation은 [count, summarize, list] 중에서만 쓴다. 수나 인원을 물으면 count, 요약·정리·설명을 요청하면 summarize, 응답자나 응답을 보여 달라거나 나열해 달라고 하면 list다.
- operation에서 정렬을 요청했는데 출력 방식 표현이 없으면 list다. 그 밖에 어느 것인지 알 수 없으면 null이다.
- sort는 operation이 list일 때만 쓰고, by와 order를 모두 쓴다. sort.by는 발화에 나온 기준 표현을 그대로 쓴다. sort.order는 [asc, desc] 중에서만 쓴다. "적은 순", "어린 순", "낮은 순", "오름차순"은 asc, "많은 순", "높은 순", "내림차순"은 desc다. 방향 없이 "나이순"처럼만 말하면 asc다.
- 출력은 JSON 객체 하나만 쓴다. 설명, 코드 펜스, 주석을 붙이지 않는다.

예시 1
입력: 소프트웨어학과 4학년 학생들을 나이 기준 내림차순으로 보여줘.
출력: {"conditions":["소프트웨어학과","4학년"],"match":"all","operation":"list","sort":{"by":"나이","order":"desc"}}

예시 2
입력: 응답 결과를 알려줘
출력: {"conditions":[],"operation":null}

## 필드 → 함수 인자 (하드/소프트)

파서의 출력이 어디로 가는지 적는다. 오른쪽 열에 답하지 못하는 필드는 지운다. **하드**는 위반 시 후보 탈락, **소프트**는 점수 가감이다.

- 입력(사용자 발화 예시 — 실제 말투로): "소프트웨어학과 학생들 중에서 4학년인 학생의 수를 알려줘"
- 출력으로 뽑을 구조(강의 2 온톨로지의 어느 클래스인가): RequestContext

| 필드 | 어느 함수의 어느 인자로 가는가 | 필터에서 어떻게 쓰이나 | 수집 필수인가 |
| --- | --- | --- | --- |
| `conditions` | `filter(RequestContext)` 내부의 `satisfy_conditions()` — 각 조건을 Form의 문항·선택지에 매칭해 응답과 대조 | **하드 필터**. 조건을 만족하지 않는 응답은 결과에서 제외 | 키는 필수. 빈 배열 []은 "조건 없음(전체 응답 대상)"으로 정상 진행. 조건이 문항·선택지에 매칭되지 않으면 추측하지 않고 되묻는다 |
| `match` | `filter(RequestContext)` 내부의 `match()` — 조건별 결과를 결합. all=모두 만족, any=하나 이상 만족, not=나열한 조건 중 어느 것에도 해당하지 않음 | **하드 필터**. 결합 방식에 따라 결과에 포함되는 응답이 달라진다 | 조건이 2개 이상인데 match가 생략되면 되묻는다. 조건이 1개 이하이고 부정 표현이 없으면 쓰지 않는다 |
| `operation` | `filter(RequestContext)` 내부의 `operate()` — count=개수, summarize=요약 설명, list=응답 나열 | 거르지 않음. 필터 결과를 어떤 형태로 보여 줄지만 정한다(출력 방식) | **수집 필수**. null이면 결과를 만들지 않고 되묻는다 |
| `sort` | `operate()` 내부의 `sort()` — by(기준 문항)의 응답 값으로 order(asc/desc) 순서 지정. 값이 같으면 응답 id 오름차순, 빈 값(미응답)은 asc·desc와 관계없이 맨 뒤 | 거르지 않음. 응답을 제외하지 않고 순서만 결정한다 | 선택. 발화에 정렬 표현이 없으면 키 생략. operation이 list가 아닐 때 sort가 오면 후처리에서 버리고 진행한다 |

| 3 | 모호한 값(결합 방식) | "소프트웨어학과, 컴퓨터공학과 학생 수 알려줘" | 프롬프트 규칙(나란히 말하면 all)대로 `match: all`이 나와 스키마 통과. filter 단계에서 두 조건이 같은 단일 선택 문항(학과)에 속하는데 all로 묶인 것을 감지 → 결과가 항상 0명인 모순 | 0명이라고 답하지 않고 "두 학과 중 하나라도 해당하는 학생을 셀까요?"라고 되묻는다 |

| 5 | 지원 밖 요청 | "4학년 학생들의 평균 나이를 알려줘" | 프롬프트 규칙으로 enum에 없는 average는 쓰지 못해 `operation`이 null로 나와 스키마 통과. 애플리케이션의 필수 조건 검사(`operation`이 null)에서 걸림. 값이 새면 `enum` 위반 → 검증 실패 | 모델을 다시 부르지 않고 2번처럼 되묻는다: "평균 같은 통계는 아직 지원하지 않아요. 4학년 학생들의 인원 수, 요약, 응답 목록 중 무엇을 볼까요?" — 평균을 지원하지 않는다는 사실을 함께 알려, 사용자가 다른 결과를 평균으로 오해하지 않게 한다 |

| 7 | 설문에 없는 조건 | "경영학과 학생 수 알려줘" (학과 선택지에 경영학과가 없음) | 스키마 통과. filter 단계에서 Question·선택지와 대조 → 매칭 실패 | 0명이라고 답하지 않고, 해당 선택지가 없음을 알리며 비슷한 선택지 목록을 보여 주고 되묻는다 |
| 8 | 이중 부정 | "3번 문항에 답하지 않은 학생 수 알려줘" | 출력에 `"3번 문항 - 미응답"`과 `"match": "not"`이 함께 나와도 스키마 통과. 후처리에서 미응답 조건과 not이 함께 있는 조합을 감지 | 확정된 요청("3번 문항 미응답자 수")을 보여 주고 확인받는다 |
| 9 | 스키마에 없는 키 | "학년별로 인원 수 알려줘" → 출력에 `"group_by": "학년"` | `additionalProperties: false` → 검증 실패 | 오류 메시지를 붙여 1회 재요청. |
| 10 | JSON 아님 또는 절단 | `stop_reason`이 `max_tokens`, 파싱 실패 | 응답 상태 확인과 JSON 파싱 | 1회 재요청 |
| 11 | list가 아닌데 sort가 옴 | "4학년 학생 수를 나이순으로 알려줘" → 출력에 `"operation": "count"`와 `"sort"`가 함께 옴 | "sort는 list일 때만"이라는 규칙은 스키마로 막지 않아 스키마 통과. 후처리에서 operation이 list가 아닌데 sort가 있는 조합을 감지 | 개수·요약에는 순서가 결과에 영향을 주지 않으므로 sort를 버리고 그대로 진행한다. 재요청하지 않는다 |
| 12 | 긍정·부정 조건 혼합 | "소프트웨어학과가 아닌 4학년 학생 수 알려줘" | 프롬프트 규칙으로 match가 생략되어 스키마 통과. 필수 조건 검사에서 "조건 2개 이상 + match 생략"으로 걸림. match가 새어 `not`으로 나오면 "소프트웨어학과도 4학년도 아닌 학생"이라는 다른 뜻이 되므로, 이 입력은 회귀 세트에서 match 생략 여부를 반드시 확인한다 | 모델을 다시 부르지 않고, 부정이 섞인 조건은 v1에서 한 번에 처리할 수 없음을 알리며 "4학년 학생 수"와 "소프트웨어학과가 아닌 학생 수"처럼 나눠 묻도록 안내한다 |

- 재요청하는 오류 유형: 형식 오류(4 범위 위반, 9 스키마에 없는 키, 10 JSON 아님·절단) / 재요청 횟수: 1회 / 초과 시 폴백 동작: 2회 연속 형식 오류면 파싱을 포기하고 사용자에게 요청을 다시 말해 달라고 되묻는다. 추측해서 진행하지 않는다. 정보 부족·모호한 값·의미 오류(2, 3, 5~8, 12)는 같은 입력을 다시 보내도 해결되지 않으므로 재요청하지 않고 되묻거나 확정 요청을 확인받는다. 11은 결과에 영향이 없는 조합이라 후처리에서 sort만 버리고 진행한다.
- v1의 한계: match가 조건 전체에 하나만 걸리므로 긍정 조건과 부정 조건이 섞인 요청("소프트웨어학과가 아닌 4학년")은 표현할 수 없다. v1은 12번처럼 match를 생략시켜 되묻기로 막고, 조건마다 부정 여부를 다는 방식(예: 조건별 `negate`)은 온톨로지를 고치는 v2 결정으로 남긴다.
