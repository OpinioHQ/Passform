## 1. 요약

- **돌아가는 것:** 응답 제출과 결과 탐색이 노트북에서 실제 LLM까지 끝까지 돈다. 숫자는 시드 원문과 코드로 대조해 일치했다.
- **가장 큰 위험:** 구현량이 아니라 **파서**다. 없는 학과를 물으면 조건을 버려 전체 건수(38명)가 나갔다. 코드 보정으로 막았고, 프롬프트 개선은 사람이 정해야 한다(3절).

- **좋은 소식:** `build.gradle`과 잠긴 타입 8개, `ConditionEvaluator`를 고치지 않고 전부 만들 수 있었다. 기존 골든 18건도 그대로 통과한다.
- **남은 결정:** 파서 처리 방식(3-6절).

## 3. 파서 문제

### 3-1. 실제 출력에서 나온 실패 패턴

프롬프트는 `src/response_analysis/prompts/parse_query.md` v2, 모델 `gpt-6-luna`, effort none, temperature 0.

| 패턴 | 입력 | 실제 출력 | 위험 |
|---|---|---|---|
| 조건을 통째로 버림 | 수의학과 학생 수 알려줘 | `{"conditions":[],"match":"all","operation":"count"}` | **틀린 숫자(전체 건수)** |
| 부정을 안 풂 | 소프트웨어학과가 아닌 학생 수 알려줘 | `conditions:["소프트웨어학과가 아닌 학생"], match:"all"` | 되묻기로 빠짐, AC78 흐름 실패 |
| 명사를 붙임 | 경영학과 학생 수 알려줘 | `conditions:["경영학과 학생"]` | 규칙 매칭 실패 → LLM 호출 증가 |
| 조건을 한 덩어리로 묶음(가끔) | 소프트웨어학과 4학년 몇 명이야? | `conditions:["소프트웨어학과 4학년"]` | 되묻기로 빠짐 |
| `topic`에 복사 | 지원 동기 요약해줘 | `target:"지원 동기", topic:"지원 동기"` | 유형 D로 잘못 가서 근거 부족 |
| 일반어를 target으로 | 설문조사 결과 요약해줘 | `target:"설문조사 결과", topic:"설문조사 결과"` | 전체 요약이 안 됨 |
| 주제가 조건으로 샘 | 비용이 부담된다는 의견 요약해줘 | `conditions:["비용이 부담된다는 의견"], target:"의견"` | 되묻기로 빠짐 |
| `match`를 항상 붙임 | 전체 응답 수 알려줘 | `match:"all"` | 무해. 규칙과 다름 |
| `operation`이 흔들림 | 소프트웨어학과가 아닌 4학년 수 | 실행마다 `count` 또는 `null` | 되묻기 순서가 달라짐 |
| 미응답 형식 안 지킴 | 3번 문항에 답하지 않은 학생 수 | `conditions:["3번 문항에 답하지 않은"]` | 되묻기로 빠짐 |

### 3-2. 측정

프롬프트 규칙대로의 기대값을 둔 16개 질문으로 쟀다.

| 설정 | 일치 |
|---|---|
| 현재 프롬프트, effort none | 5~6/16(실행마다 다름) |
| 현재 프롬프트, effort low | 5/16 |
| 입력을 `<query>`로 감쌈 | 5/16 |
| 입력을 `입력: … 출력:` 형식으로 | 5/16 |
| **현재 프롬프트 + 예시 7개, effort none** | **13/16** |

- 같은 입력 반복: "수의학과 학생 수 알려줘" 6회 중 5회 조건을 버림, 1회는 `수의학과 학생`. "소프트웨어학과 4학년" 6회는 모두 정상(앞선 실행에서는 한 덩어리로 묶인 적 있음). **temperature 0이어도 출력이 달라진다.**
- 해석: 모델 설정이 아니라 프롬프트 문제다. 다만 **13/16은 예시를 쓰기 전에 본 질문으로 잰 값이라 낙관적이다.** 예시는 다른 낱말(영문과 등)로 썼지만 패턴은 보고 썼다.
- 남은 3건: `match:"all"` 생략(무해), `소프트웨어학과 지원자`, `비용이 부담된다는`.

### 3-3. 지금 코드에서 막는 방법 (임시, `ParsedContextRepair`)

호출 위치 `src/main/java/com/opinio/passform/demo/service/AnalysisService.java:102`. 통계 요청이 아니고 `{query}`일 때만 탄다. `{context}`는 타지 않는다.

1. 원문 낱말 중 일반어도 아니고 파서 출력에도 없는 것을 조건으로 되살린다(`demo/domain/analysis/ParsedContextRepair.java:112`, 일반어 목록 `:34`). → "수의학과" 복구 후 `unknown_condition`.
2. `~가 아닌`, `~제외` 등을 풀어 조건 하나면 `match: not`으로 바꾼다.
3. 긍정·부정이 섞이면 원문 그대로 두고 `match`를 비운다. → `missing_match`, 선택지 없음(AC26).
4. `~에 답하지 않은` → `문항 - 미응답`, `~에 답한` → `문항 - 응답`.
5. 조건 끝의 일반 명사(학생, 지원자 등)를 뗀다.
6. 낱말이 전부 선택지면 조건을 나눈다(`소프트웨어학과 4학년`).
7. `target`·`topic`이 같으면 문항을 가리키는지로 가른다. 일반어뿐이면 버린다. 조건으로 샌 표현도 뺀다.
8. `topic`이 있는데 `target`이 문항이 아니면 `target`을 버린다. `~는 의견` 꼬리를 뗀다.
9. `operation`이 `null`인데 "수·몇 명" 표현이 있으면 `count`로 둔다.
10. 조건이 1개 이하면 `match`를 지운다(`not` 제외).

입력은 태그 없이 발화 그대로 보낸다(`demo/llm/QueryParser.java:52`).

### 3-4. 보정의 한계

- 낱말 목록 기반이다. 한국어 표현을 다 담을 수 없다.
- 지나치면 **불필요한 되묻기**가 된다: "둘 다", "상위 3명", "오늘". 틀린 숫자는 아니지만 데모에서 답답할 수 있다.
- 못 막는 경우: 버려진 낱말이 일반어 목록에 있을 때, 매처가 비슷한 선택지에 잘못 붙일 때(스파이크 E40, E35).
- 그래서 화면에 해석("이렇게 이해했어요")과 근거를 숫자 위에 둔다. 사람이 틀린 해석을 알아볼 마지막 장치다.
- **프롬프트를 고쳐도 보정은 남겨야 한다.** 조건을 버리는 일이 6회 중 5회였고 temperature 0에서도 흔들린다.

### 3-5. 프롬프트 v3 안 (사람 승인 전, 저장소 프롬프트는 안 고침)

`parse_query.md`의 예시 4 뒤에 붙이는 안이다. 평가 질문과 겹치지 않게 가상의 "영문과"로 썼다.

```
예시 5
입력: 영문과 학생 수 알려줘
출력: {"conditions":["영문과"],"operation":"count"}

예시 6
입력: 영문과가 아닌 학생 몇 명이야
출력: {"conditions":["영문과"],"match":"not","operation":"count"}

예시 7
입력: 전체 몇 명이야
출력: {"conditions":[],"operation":"count"}

예시 8
입력: 영문과가 아닌 2학년 수
출력: {"conditions":["영문과가 아닌","2학년"],"operation":"count"}

예시 9
입력: 2번 문항에 답하지 않은 사람 수
출력: {"conditions":["2번 문항 - 미응답"],"operation":"count"}

예시 10
```

1. 파서 출력 보정 단계(`ParsedContextRepair`).
2. 파서에 발화를 태그 없이 보냄.
3. **분기 건너뜀 판정(`demo/domain/analysis/PathAwareEvaluator`):** 잠긴 타입을 안 바꾸려고 건너뛴 문항이 같은 응답끼리 묶어 평가한 뒤 합침. §3의 q6 한계를 메우지만 **골든이 없어 수용된 것이 아니다.** 기존 2차 위임 계획과 겹치니 어떻게 할지 정해야 한다.
4. 선택지 문구가 버전 사이에 바뀐 문항의 정렬은 `unsortable_field`.
5. 문항 표현 해석(`demo/domain/analysis/QuestionResolver`): 번호는 최신 버전 기준, 문구는 공백 무시 일치, 없으면 포함 관계.
6. 규칙 매칭 우선, 어느 버전에서도 못 푼 조건만 LLM 매처(규칙으로 일부 버전이 풀리면 나머지 버전은 판정 불가).
7. `503 llm_unavailable`, `400 invalid_option`.
8. 전체 요약에서 숫자·날짜만 있는 단답 제외.
9. 상한을 넘은 주제는 `기타`로 합침(주제 수 상한 6은 임시).
10. AI 고지 문구를 코드 상수로 둠(`demo/service/FormQueryService.java:109`). SPEC 158행은 첫 배포 때 폼에 기록해 고정하라고 한다. **SPEC과 다르다.**
11. 답과 폼 정의를 JSON 문자열로 저장, 문항 테이블 없음.
12. 비소유 폼 분석은 403, 남의 제출 이력은 404.
13. 데모 계정 전환 헤더 `X-Demo-User`.

## 6. MVP 개발을 위해 발견한 사항

### 6-2. AI 분석

- 코드로 숫자를 정하는 구조(`ConditionEvaluator`)는 실제 파서·매처와 붙여도 그대로 동작했다. **위험은 평가 함수가 아니라 그 앞단이다.**
- 파서·매처 품질을 잴 세트가 필요하다. 2-3절의 질문과 3-1절의 실제 출력을 재료로 쓸 수 있다. `evals/`에 넣을지 정한다.
- 미지원 요청의 안내가 부족하다. "3학년 이상", "상위 3명", "오늘"이 전부 "조건을 찾지 못했어요"로 나온다. 왜 안 되는지 말해 주는 문구나 규칙이 필요하다.
- 범위 규칙은 명시적 표현만 잡는다. "수정 전 응답만"은 이번엔 매처 덕에 막혔을 뿐이다.
- 질문 안의 인젝션("이전 지시를 무시하고…")도 이번엔 우연히 막혔다. 응답 원문뿐 아니라 질문 쪽도 레드티밍 대상에 넣는다.
- 토큰은 적다(질문 1건에 파서 약 1,200 + 매처 약 3,200 입력). 지연이 더 큰 문제다.
- `gpt-6-luna`, `gpt-6.1-terra`, `text-embedding-3-small` 모두 실제 호출 성공을 확인했다.

### 6-3. 데이터·DB

- 폼 정의를 버전별 JSON으로 저장하는 안은 버전 판정·제출 이력·통계에 잘 맞았다. 문항 테이블 없이 다 됐다.
- 다만 필터·집계를 전부 메모리에서 한다. 폼 하나의 응답을 매번 전부 읽는다. 데모 규모는 문제없고 부하는 안 쟀다.
- `response_id`는 UUID로 저장했다. 정렬 없는 목록이 ID순이라 **제출 순서와 무관하게 섞여 보인다.** 규칙대로지만 화면에서 어색하다.
- 스키마 이관 도구가 없다. `ddl-auto=update`는 데모 전용으로만 쓴다.
- 조회가 건별로 나간다(`myForms`, `history`). 데모 규모에선 문제없다.
- JSON 컬럼 대신 `text`를 썼다. Jackson 3와 Hibernate JSON 매핑을 시험하지 않으려는 선택이었다. 필요하면 재검토한다.
- 임베딩 저장소가 없다. `config/rag.yaml`을 쓸 때 메모리 계산으로 충분한지 정한다.

### 6-4. 로그인·보안

- `Authentication.getName()`을 사용자 ID로 쓴다. 소셜 로그인을 붙이면 제공사 ID ↔ `User` 매핑과 첫 로그인 시 생성이 필요하다.
- `demo/config/DemoSecurityConfig`는 경로를 좁힌 별도 체인으로 기존 `config/SecurityConfig.java:19`를 안 고치고 공존한다. 소셜 로그인 구현에는 쓰지 않는다.
- 데모 체인은 인증이 없다. `X-Demo-User`로 아무나 될 수 있으니 **외부 공개 금지**. 127.0.0.1 바인딩으로 막아 뒀다.
- 소유권 판정은 service에 있어 로그인 방식이 바뀌어도 유지된다.

### 6-5. 코드 구조·MVP에서 챙길 것

- `src/main/resources/application-demo.properties`의 snake_case, `open-in-view=false`는 본 설정에도 필요하다. 없으면 API가 camelCase로 나온다.
- 분기 경로 계산이 Java(`demo/domain/form/ResponsePathCalculator`)와 TS(`frontend_demo/src/lib/responsePath.ts:28`)에 둘 다 있다. 서버가 다시 계산하니 안전하지만 규칙이 바뀌면 둘 다 고쳐야 한다.
- `demo/config/AnalysisProperties`의 값을 `config/rag.yaml`로 옮길지 정한다(강의 6: 파라미터 분리).
- 소소한 정리: `toLowerCase()`에 `Locale` 없음(`MeService`, `DemoSeedLoader`), 예외 메시지를 에러 코드로 쓰는 방식.

### 6-6. 테스트·골든·CI

- **`ConditionEvaluatorGoldenTest.java:228`이 YAML 최상위 `cases`를 전부 평가 함수 케이스로 읽는다.** 되묻기·결과 처리 골든을 같은 곳에 넣으면 빌드가 깨진다. 기능별 최상위 키가 필요하다.
- 사람이 먼저 쓸 골든 후보: AC22, AC25, AC26, AC27, AC29, AC30, AC32, AC77, AC28, AC61, AC87, AC93, 그리고 q6(`rb05`·`rb09`).
- 분석 API 테스트 입력으로 3-1절의 실제 파서 출력을 쓰면 모의 파서가 실제와 비슷해진다. `src/test/java/com/opinio/passform/demo/domain/analysis/ParsedContextRepairTest.java`가 그렇게 돼 있다.
- CI는 `./gradlew build`뿐이고 프론트 검사가 없다(`ci.yml`).
- 실제 DB 테스트가 없다. 저장소 쿼리는 실행으로만 확인했다. CI에 Postgres를 넣거나(ci.yml 주석) 테스트 DB를 정한다.
- 커버리지 측정이 service·domain뿐이라(`build.gradle:64-65`) `llm`, `controller`, `config`는 숫자에 안 잡힌다.
- 브라우저 점검을 저장소에 넣을지, E2E 도구를 정할지 결정한다. 이번 31건(9절 반영 전)이 출발점이 된다.

### 6-7. 화면

- `matched`에 `question_id`만 있어 근거가 "버전 2의 q11"로 보인다. **제작자는 이해 못 한다.** 문구가 필요하다(SPEC 후보).
- 해석 칩이 "주말에 활동하고 싶은"처럼 원문으로 나온다. 실제 매칭("희망 활동 시간 = 주말")을 보여 주는 편이 낫다.
- 목록이 응답 ID만 보여 준다. UUID는 읽을 수 없으니 제출 시각이나 답 일부가 필요하다.
- `unknown_condition` 후보가 버전별로 반복되고(v1 학년, v2 학년…) 글자뿐이다. 묶어서 누를 수 있게 한다.
- 판정 불가 안내가 "문항이 없거나 분기로 건너뜀"으로 뭉쳐 있다. API가 이유를 구분해 주지 않는다.
- 요약 10초 이상 기다리는 동안 "분석 중…"뿐이다. 단계 표시가 필요하다.
- `기타` 11건에 "근거가 부족해…"가 뜨면 실패처럼 보인다.
- 응답 화면에 `payment_link`, 첨부, 진행 표시가 안 나온다. 새로고침하면 답이 사라진다.
- 응답자·제작자 전환이 단순 메뉴다. `ui_mode`를 저장하지 않는다(`PATCH /me/settings`는 있으나 화면 미사용).
- 데모 계정 선택은 시연용이다. 정식 화면에서는 뺀다.
- 360px 가로 스크롤 없음은 확인했다. 실제 휴대폰, 키보드가 열린 상태는 안 봤다.

### 9-1. 전화번호

- 재현: API는 `400 invalid_input_format_value`, 화면도 "제출했습니다"가 안 나옴. 응답 수 67건 그대로. 저장된 응답 중 그 값도 없음. 다만 19:53에 DB를 초기화해서 그 전 기록은 확인할 수 없다.
- 실제 결함: 화면이 형식을 안 봐서 "다음"이 그냥 넘어가고, 동의까지 끝낸 맨 마지막에야 거부했다. 넘어가니 통과한 것으로 보였을 수 있다.
- 수정: `frontend_demo/src/lib/answerFormat.ts` 추가. "다음"을 누를 때 필수·형식·글자 수를 문항 아래에 바로 알린다. 입력란 아래 형식 안내도 추가했다. 서버 검사는 그대로 최종 기준이다.

### 9-2. 버튼

- 원인: 버튼을 동아리 폼 기준으로 코드에 박아 두었다. 평균·버전·수의학과처럼 되묻기를 보여 주려던 예시가 섞여 있었고, 다른 폼에서는 "주말", "지원 동기" 버튼도 안 되는 요청이었다.
- 수정: `frontend_demo/src/lib/exampleQuestions.ts`. 통계 결과와 공개 폼 정의로 버튼을 만든다. 응답이 있고 한 문항에만 있는 선택지만 쓰고, 예·아니요는 뺀다. 요약 버튼은 AI 요약을 켠 폼의 비개인정보 장문 문항으로만 만든다.
- 버튼은 파서를 거치지 않고 확정 요청(`{context}`)을 바로 보낸다. 그래서 되묻기로 빠지지 않고 빠르다. **대신 버튼으로는 자연어 파서를 보여 줄 수 없다.** 시연에서 자연어를 보이려면 직접 입력해야 한다.
- 직접 입력한 "평균 나이"는 지금처럼 안내한다.

### 9-3. 제작자 화면 문구

- 바꾼 것: "판정 불가" 제거, `q11`을 문항 이름으로, 응답 ID를 "응답 1"로, `v1`을 "폼 버전 1"로, "결과를 추측하지 않고 다시 묻습니다"를 "조금 더 알려 주세요"로, "AI가 라벨을 붙이고 코드가 센 주제"를 "답을 주제별로 묶었어요"로. 근거에서 응답 ID도 뺐다.
- 이유 설명(문항 없음·분기 건너뜀·미동의 제외)은 물음표를 눌러야 보인다(`frontend_demo/src/lib/resultText.ts`, `ui.tsx`의 `Explained`).
- **요청과 다르게 한 것:** "전체 39건 중 확인할 수 있는 17건에서 찾았어요"는 항상 보인다. 이 문구까지 숨기면 "6건"이 39건 전체를 본 숫자로 읽힌다. 절대 규칙 3과 AC75·AC78이 범위 표시를 요구한다. 위치와 크기는 와이어프레임에 맞춰 조정할 수 있다.
- API 변경: `matched[]`에 `question_note` 추가(`demo/service/AnalysisResponse.java`). 측정 당시 SPEC에 없던 필드라 2026-11-05에 253행·270행·314행에 반영했다. `coverage`는 그대로 둔다.
- 6-7절에서 해결된 것: `q11` 표시, 해석 칩의 원문 표시, 목록의 UUID, 되묻기 후보의 버전 반복, `기타`가 실패처럼 보이던 문구. 남은 것: 판정 불가 이유를 API가 구분하지 않아 화면이 `matched`로 추정하는 점, 긴 대기 중 진행 표시, 응답 화면의 송금 링크·첨부·진행 표시, 새로고침 시 답 유실.
- 결과 대시보드의 배치는 와이어프레임을 받은 뒤 고친다.
