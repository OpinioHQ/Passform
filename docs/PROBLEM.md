# 문제 정의서 — Passform

> 이 문서는 **왜** 만드는가에 답한다. 무엇을 만드는가는 `docs/SPEC.md`, 도메인 구조는 `docs/ontology.yaml`이 정본이다.
> 로그 번호와 관찰 번호는 `docs/research/interviews.md`(강의 2)의 번호다. 따옴표 안은 기록 원문이고, 따옴표 없는 문장은 요약이다.

## 1. 한 문장 문제

소속 활동으로 여러 폼에 응답하는 대학생은 작성 중 남은 분량을 알기 어렵고, 나중에 답하려던 폼의 마감을 놓치거나 제출한 답을 다시 확인하기 어려워 응답 과정과 내역을 스스로 관리하기 어렵다.

> 2차 문제(운영진): 폼을 만들어 응답을 모으는 대학생 운영진은 모인 응답을 확인·정리하려고 응답 화면과 엑셀 시트를 오가며 수작업을 한다.

## 2. 대상과 비대상

- 1차 사용자(응답자): 동아리 가입, 학생회 행사, 학과 신청처럼 소속 때문에 폼에 반복해서 응답하는 대학생
- 2차 사용자(운영진): 그런 폼을 만들어 응답을 모으고 선발·명단 정리에 쓰는 대학생 운영진(동아리, 학생회, 프로젝트 모임)
- 비대상(현재)
  - 직장 내 만족도 조사 응답자 — 선택지 과세분화, 획일적 질문(로그 7)은 폼 제작 품질의 문제라 이번 범위가 아니다.
  - 보상을 받으려고 설문에 참여하는 응답자 — 보상 불신(로그 8)은 보상 기능과 함께 다룬다.
  - 통계 분석이 목적인 연구·학술 설문 작성자 — 평균, 교차분석, 검정이 필요하다.
  - 회비 입금을 대조하는 총무 — "실제 은행 송금·결제 처리"는 온톨로지 범위 밖이다. Passform은 송금 링크만 연결한다.

## 3. 증거

응답자

- 작성 중 폼의 전체 분량을 가늠하기 어렵다. “페이지가 계속 넘어가는데 전체 챕터가 얼마나 남았는지 안 떠서 소요 시간을 알 수 없는 게 제일 불편해요.” (로그 9) / 같은 페인: 로그 4 (`전체분량_파악_어려움`). 현재 진행률 파악은 로그 9에 기록된 별도 신호다.
- 받은 폼의 마감을 놓친다. "마감일이 지나서 폼 제출을 못한 적이 많아요" (로그 2) / 나중에 응답하려다 마감을 놓친 경험(로그 7, 직장인). 대학생 대상 발생 건수에는 로그 7을 합산하지 않는다.
- 제출한 뒤 무엇을 썼는지 확인할 수 없어 불안하다. "제출 누르면 '내가 제대로 썼나?' 싶어서 불안해요. 완료 후에 내가 선택한 전체 내용을 확인할 수 있으면 좋겠어요." (로그 6) / 같은 페인: 로그 3, 4 (응답자 페인 2)
- 같은 기본 정보를 폼마다 다시 쓴다. "이름이나 전화번호처럼 매번 똑같이 쓰는 기본 정보는 알아서 자동으로 입력되면 좋겠어요." (로그 3) / 개인정보·텍스트를 직접 입력하는 번거로움 (로그 8, 페인 코딩)
- 개인정보를 내는 것 자체가 불안하다. "설문조사에 개인정보를 제출해야하는 것이 불안해요" (로그 4) / 같은 태그: 로그 9 — 정보를 저장해 주는 방식이 이 불안을 키울 수 있다(Job Story 2의 Anxiety). 그래서 프로필 저장 항목을 닫힌 목록으로 제한하고, 프로필 삭제를 허용하며, 수집 범위를 동의 문구로 보여 준다(SPEC AC3, AC5, AC13).
- 송금하려고 폼 밖으로 나간다. "계좌이체나 과거 이력 등을 확인하려고 외부 창을 자주 왔다 갔다 하는데, 이 때문에 설문 흐름이 끊기는 경우가 많아요." (로그 10) / 관찰 2에서 계좌번호를 보고 은행 앱으로 1번 이동했다. 송금 링크는 계좌번호를 옮겨 적는 수고만 줄인다 — 로그 3의 "'송금완료' 체크만 해두고 실제론 돈을 안 내는" 입금 대조 문제는 링크로 풀리지 않고 범위 밖이다.
- **반대 신호:** 관찰 2에서 각종 개인정보 입력은 30초 안에 끝났다. 시간이 오래 걸린 것은 주관식 2문항(각 5~10분)이었다. 자동채우기의 가치는 시간 단축보다 반복·오입력·불안을 없애는 데 있다는 뜻이다. 그래서 작성 시간 단축을 성공 지표로 쓰지 않는다. 주관식 작성 부담은 캡디 추가 개발 2순위(AI 다듬기)로 다룬다.

운영진

- 응답을 확인하려고 응답 탭(통계)과 연동 시트를 5번 번갈아 보고, 면접 단계에서는 창을 나눠 폼과 시트를 함께 띄웠다. 본인은 기존 템플릿과 회의록을 보느라 이동이 많았다고만 진술했다 — 응답 확인 단계의 전환은 관찰에서 처음 드러났다. (관찰 1 ⑦·⑧, 로그 3의 응답자)
- "결과를 엑셀과 연동해서 사용하는 것이 어려웠어요" (로그 2) / 자체 분석 기능이 부족해 결과를 외부 도구와 연동해 쓴다 (로그 1, 2 — 제작자 페인 2)
- 질문 수가 많으면 문항을 하나씩 만들어야 하고, 기본 문항도 매번 다시 만든다. "질문의 수가 많을 때 따로따로 다 만드는게 힘들었어요" (로그 1) / 같은 페인: 로그 3 (제작자 페인 1). 관찰 1에서 이전 템플릿을 보려고 다른 설문지를 4번 열었다.

## 4. 반증 조건

### 문제의 실재 (인터뷰 증거로 지금 판정)

기준선은 단골 예시와 같은 비율(대상의 30%)이다. 이 기준은 로그를 본 뒤에 정했으므로, 다음 인터뷰 라운드(사용자 테스트 사전 인터뷰 포함)에서 같은 기준으로 다시 판정한다.

**층 A — 응답자**

- 주장: 소속 때문에 폼에 반복 응답하는 대학생은 작성 중 전체 분량 파악의 어려움, 마감 누락, 제출 내용 재확인의 어려움 중 하나 이상을 겪는다.
- 반증 조건: 대학생 인터뷰 대상 중 세 문제 중 하나 이상을 겪은 사실이 인용·태그·로그별 페인에 기록된 사람이 **30% 미만이면 기각**한다.
- 현재 집계: 대학생 7명(로그 1, 2, 3, 4, 6, 9, 10) 중 5명(로그 2, 3, 4, 6, 9) = 약 71% → **유지.** 로그 3·4의 제출 내용 재확인 어려움은 태그·로그별 페인 설명으로, 로그 9의 전체 분량 파악 어려움은 인용과 태그로 확인했다. 로그 7의 마감 누락은 직장인 사례라 대상 발생 건수에 합산하지 않았다.

**층 B — 운영진**

- 주장: 응답을 모으는 대학생 운영진은 응답을 확인·정리하는 데 폼 밖 도구와 수작업을 쓴다.
- 반증 조건: 폼 제작 경험이 있는 인터뷰 대상 중 응답 확인·정리 부담이 기록된 사람이 **30% 미만이면 기각**한다.
- 현재 집계: 5명(로그 1, 2, 3, 6, 8) 중 5명 → **유지, 약한 근거.** 행동으로 확인한 것은 관찰 1(로그 3의 응답자) 1명이고, 로그 2는 진술, 로그 1, 6, 8은 팀의 페인 코딩이다. 다음 인터뷰에서 "지난번 폼 응답을 마지막으로 정리한 게 언제였고, 어떻게 했나요?"로 행동을 확인한다.

### 해결 가설 (제품 사용 관찰로 이후 판정 — MVP 사용자 테스트)

- 가설 1(제출 이력·자동채우기): 제출한 응답을 다시 확인하고 저장한 프로필로 응답자 본인 정보 문항을 채울 수 있으면, 응답자는 제출 후 확인 불안과 기본 정보 반복 입력 수고를 덜 겪는다.
  - 반증 조건: **제출 이력에서 내 답을 확인할 수 있는데도** 무엇을 제출했는지 알아보려고 제작자에게 문의하거나 별도 기록을 찾거나, **값이 맞게 채워졌는데도** 지우고 다시 입력하거나, 자동채우기 가능한 본인 정보 문항이 있는 다음 폼에서 직접 입력하면 기각한다. 값이 잘못 채워져 고친 경우는 자동채우기 품질(SPEC AC6)의 문제로 따로 센다. 동일 폼에 다시 제출했다는 사실만으로는 기각하지 않는다.
- 가설 2(내 폼함·마감 알림): 받은 폼을 내 폼함에 저장하고 마감 전에 알려 주면, 응답자는 마감을 놓치지 않는다.
  - 반증 조건: 사용자 테스트에서 참가자를 알림 켬·끔 그룹으로 나눴을 때(`PATCH /me/settings`), **알림이 정상 발송됐는데도** 켠 그룹의 마감 전 제출률이 끈 그룹보다 높지 않으면 기각한다. 발송 실패·중복 발송은 알림 품질(SPEC AC18)의 문제로 따로 센다.
- 가설 3(AI 결과 탐색): 자연어 한 줄 요청을 실제 문항·선택지에 매칭해 세거나 나열하고 어떻게 매칭했는지 함께 보여 주면, 운영진은 응답을 시트로 옮겨 다시 세지 않는다.
  - 반증 조건: 사용성 세션에서 관찰 1 ⑦단계(응답 확인)와 같은 과제를 줬을 때, **요청대로 매칭된 결과를 받고도** 시트를 열어 같은 조건으로 다시 세면 기각한다. 매칭이 틀려서 다시 센 경우는 매칭 품질(SPEC AC21)의 문제로 따로 센다.

## 5. 성공의 정의

MVP 배포 후 100명 이상을 대상으로 한 사용자 테스트에서 잰다.

응답자

- 마감 전 제출률: 내 폼함에 저장한 폼 중 마감 전에 제출한 비율(알림 켠 그룹 / 끈 그룹)
- 제출 이력 확인 성공률: 로그인 응답자가 도움 없이 자신의 과거 문항·답변을 제출 이력에서 찾아 확인한 비율
- 자동채우기 사용률: 로그인 응답자 중 프로필로 채운 비율
- 채운 값 유지율: 자동으로 채운 값을 고치지 않고 제출한 비율
- 프로필 저장 거부·삭제율: 개인정보 불안의 신호. 높으면 저장 방식이 신뢰를 얻지 못한 것이다

운영진

- 분석 완결률: AI 결과 탐색 요청 중 결과(`status: ok`)까지 간 비율 — 되묻기 후 다시 말하거나 확정 요청을 보내 결과에 도달한 경우를 포함한다
- 사용성 세션 지표: 관찰 1 ⑦단계 과제 재현 시 폼 밖 전환 횟수(기준값 5번)

공통

- 핵심 시나리오 과업 성공률 95% 이상: 주요 사용자 시나리오(프로필 등록 → 자동채우기 → 제출 → 이력 확인, 폼 생성 → QR 배포 → 결과 탐색 등)를 사용자가 도움 없이 끝낸 비율. 계획서의 "주요 사용자 시나리오 기반 핵심 기능 테스트 95% 이상 통과"를 사용자 테스트의 과업 성공률로 정했다
- 보조 지표: Likert 평균 만족도 4.0 이상(계획서 목표). 의견 지표라 위의 행동 지표와 함께 해석한다
